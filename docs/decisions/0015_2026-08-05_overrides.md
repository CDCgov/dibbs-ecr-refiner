# 15. overrides

Date: 2026-08-05

## Status

## Context and Problem Statement

Refinement is **retention-by-inclusion**: the matching engines keep entries whose
codes are in the configured want-set and prune the rest.
[ADR 0014](0014_2026-07-29_code-exclusion.md) handles the case where a
jurisdiction wants a code to stop _pulling_ content in, by removing it from the
want-set at projection time.

This ADR handles the other case: codes a jurisdiction **never wants to appear in
the output, no matter what**--even when some other rule would otherwise retain
the entry carrying them, and even in sections refinement does not touch at all.
The motivating cases are sensitive or stigmatizing content (behavioral health,
substance use, reproductive or HIV status).

The decisive structural fact: **most sections never reach the matching engines.**
`refine_eicr` only calls `process_section` for `action="refine"` sections;
`retain`, narrative-only, and `SECTION_PROCESSING_SKIP` sections bypass it
entirely (`refiner/app/services/ecr/refine.py:473-545`). A "no matter what"
guarantee therefore cannot live in the engines--it has to be a pass over the
whole document.

> [!NOTE]
> **Terminology.** "Overrides" is the application's name for this feature, and
> code should use it. The first draft called this "suppression" throughout, which
> forces a reader to translate between the ADR and the UI. This document uses
> **overrides**; `suppress_eicr` becomes `apply_overrides`, `SuppressionPlan`
> becomes `OverridePlan`, and so on.

## Decision Drivers

- **Universal _section_ coverage.** The guarantee is worthless if it holds only in
  refinable sections. Note the qualifier: this driver is about reaching every
  section, not every representation of the data within one--see the caution on
  narrative `<text>` in _Decision Outcome_.
- **Predictable precedence.** When a code is both wanted and overridden, behavior
  must be unambiguous and require no reconciliation logic.
- **Reuse over reinvention--but only when a second consumer exists.** The
  section-aware pruner already encodes the hard part (entry-level vs.
  container-level vs. whole-entry pruning, driven by IG `EntryMatchRule`s). We
  extract shared abstractions only when we actually have two consumers.
- **Minimize CDA breakage risk.** Any removal must leave the document
  schema-valid; we cannot delete a leaf code element and leave a parent that
  `SHALL` contain it.
- **Provenance must not re-leak.** Detailed provenance would re-disclose the very
  thing the removal was meant to hide.

## Considered Options

### B1. Cross-cutting pre-pass that reuses IG rules in subtractive mode (RECOMMENDED)

Add an overrides pass, `apply_overrides`, that runs in `refine_for_condition`
(`refiner/app/services/pipeline.py:219`) **before** `refine_eicr`. The pass walks
every section in the `structuredBody` regardless of section instructions. For
each section:

- If the section has `entry_match_rules` in its `SectionSpecification`, reuse
  those rules to locate code-bearing elements, but invert the decision: prune the
  entry/container where a code matches the **override set**, using the rule's own
  strategy (`prune_container_xpath`, `preserve_whole_entry`). The "surgical vs.
  whole-entry" decision is already encoded in the rules.
- If the section has no rules, fall back to entry-level removal of any entry
  carrying an overridden code.

**Pros**

- Universal section coverage: it also reaches `action="retain"`, narrative-only,
  and `SECTION_PROCESSING_SKIP` sections--the ones refinement never visits--and
  strips overridden entries from them. (Reaching a narrative-only section buys
  nothing today, since those sections carry no entries; see the narrative caution
  in _Decision Outcome_.)
- Correct precedence for free: removing overridden codes first means the
  subsequent refinement pass cannot re-introduce them (it only retains what is
  present).
- Reuses IG rule metadata and pruning strategies instead of duplicating them.

**Cons**

- The container-prune decision is _inverted_ relative to positive refinement
  (drop matched containers, keep the rest), so the same rule metadata drives new
  keep/drop logic. This is a bounded amount of genuinely new code, not free reuse
  of `_prune_at_container_level`.
- Refinable sections are traversed twice (override, then refine). Both traversals
  are `findall` over a section's direct `<entry>` children with the same rule
  evaluation refinement already does, so the added cost is roughly one extra
  pass over already-parsed nodes--negligible against parse and serialize. It is
  listed as a cost rather than dismissed, but it is not a reason to prefer a
  design that traverses once.

### B2. Parallel generic scanner (whole-entry only)

A standalone pass that searches the whole document generically and removes any
entry containing an overridden code, without consulting IG rules.

**Pros**: simplest to write; one uniform behavior.
**Cons**: crude--cannot surgically prune an overridden sub-observation out of an
otherwise-wanted panel; either over-removes (whole entry) or reinvents the
container logic. Loses section-aware precision we already have.

### B3. Hook overrides into the matching engines only

Thread the override set into `process_section` and subtract there.

**Cons**: fails the core requirement, per the structural fact in _Context_. A
code overridden "no matter what" would survive in every section refinement does
not touch. Rejected--this is the decisive argument for a separate pass.

### Ordering: pre-pass vs. post-pass

Raised in review: if overrides ran _after_ refinement, the story "omission comes
last, so it wins" would be easy to tell.

Both orderings do give overrides precedence, so precedence does not decide it.
What decides it is **narrative reconstruction**. `reconstruct_narrative`
(`refiner/app/services/ecr/narrative/reconstruction.py:1354`) builds a section's
`<text>` _from its surviving entries_ and mutates them (stripping references,
relinking rows, stamping `typeCode="DRIV"`). A post-pass would therefore have to
remove overridden content from the entries **and** from the narrative table just
generated from those entries--re-running or post-editing reconstruction, and
re-deriving row IDs. Running first means reconstruction never sees the overridden
data, and no narrative-repair logic is needed.

This is the same species of argument as B1-over-B3: a fact about the code, not a
preference.

## Decision Outcome

> [!IMPORTANT]
> Direction not yet finalized--this document captures the recommended shape so
> the team can react before implementation.

**Option B1**, running as a pre-pass.

Resolved design decisions:

- **Scope: configuration-wide.** An override belongs to a configuration, not to a
  `(configuration, condition)` pair. Overrides are conceptually closer to custom
  codes than to TES codes: they are a jurisdiction's own list, and the management
  UI does not associate them with a condition. This **reverses the first draft**,
  which asserted condition scoping.

  The consequence is a simplification: because
  `convert_config_to_storage_payload` emits one `active.json` per configuration
  and `refine_for_condition` receives that whole payload, a config-wide deny-set
  is exactly the shape the runtime already has. The first draft spent a long
  section on how to make the deny-set honor a condition axis at a
  configuration-wide seam; with config-wide scope that problem does not exist.
  (Nor does it exist for exclusion, which resolves per-condition upstream of the
  flattening--see ADR 0014.)

  **Jurisdiction-wide overrides are deliberately deferred, not dismissed.** An
  earlier round of designs had a global override list, and review flagged that we
  would likely get a lot of value from one: a jurisdiction that never wants a code
  emitted almost certainly means it across every configuration it owns, and
  maintaining the same list per configuration is exactly the kind of duplication
  that drifts. We are starting at the configuration level to test the mechanism on
  the narrower surface first--config scope is what the storage payload, the
  management UI, and `refine_for_condition` already have, so it costs nothing to
  build and nothing to reverse. A jurisdiction-wide list is a widening of the
  lookup (union the jurisdiction's list into the config's deny-set at projection
  time); it does not change the pass, the pruning strategy, or the provenance.

- **Granularity: code + code system.** Shaping the deny-set as a `CodeSystemSets`
  reuses OID-scoped `find_match`, so "code X in SNOMED" is distinguished from
  "code X in a local system" and we avoid over-removal.
- **Provenance is minimal and content-free.** One generic per-section footnote
  line ("Data in this section was masked")--no code, count, or domain--because
  the codes are overridden precisely for their sensitivity. Nothing in the
  `trace.json` sidecar for now.

Two reframings that should survive into implementation:

1. **Coverage vs. strategy are different axes.** Coverage is universal across
   sections (every one, ignoring instructions); pruning strategy is rule-driven
   where rules exist. Collapsing these into "generic search everywhere" is what
   leads to a crude scanner. Coverage is about _sections_ reached, not
   _representations_ removed within them--see the narrative caution below.
2. **Overrides must be their own pass because most sections never reach the
   matching engines.** This should be stated as an invariant wherever the pass is
   documented.

> [!NOTE]
> **Scope: eICR only.** Overrides are an eICR-only pre-pass. If a future need
> arises to remove content from the RR, it is a separate design.

> [!CAUTION]
> **This ADR guarantees removal of _coded_ data only. Narrative `<text>` is not
> covered, and that gap is real.** The pass removes entries and containers. A
> section's `<text>` block is human-readable prose and tables written by the
> sending EHR, and there are two ways overridden content survives in it:
>
> - **`narrative="retain"` leaves `<text>` verbatim.** For a `retain` section, and
>   for a refined section whose narrative action is `retain`, the original
>   narrative is left in place even when every entry is pruned
>   (`entry_matching.py:149-151, 175`). So an override can remove the
>   machine-readable entry while the row a human actually reads survives--the worst
>   possible outcome for a feature that exists to prevent disclosure.
> - **Narrative-only sections have no entries to remove at all.** Chief Complaint,
>   Reason for Visit, History of Present Illness, and Review of Systems
>   (`refiner/app/services/ecr/policy.py:76-79`) have no entry match rules and are
>   conveyed entirely through `<text>`. These are precisely the sections most
>   likely to carry stigmatizing free text, and an entry-removal pass cannot touch
>   them. Universal _section coverage_ is not the same as universal _content
>   coverage_, and the first draft's framing blurred that.
>
> The one place the guarantee does hold end-to-end is the five
> `RECONSTRUCTABLE_SECTIONS` configured for `narrative="reconstruct"`, because
> reconstruction rebuilds `<text>` from the surviving entries--which is the
> ordering argument above, now doing double duty as the only narrative story we
> actually have.
>
> **This is deliberate scoping, not an oversight.** Removing coded data is a
> tractable, testable structural problem; masking free text is a different problem
> with different tools (reference resolution at minimum, NLP at worst) and a much
> worse failure mode. Building the coded-data pass first gives that harder work a
> place to attach: the deny-set, the per-section `content_masked` flag, and the
> pass that already visits every section are all reusable by a narrative-aware
> follow-up. **Until that work exists, overrides must not be described to
> jurisdictions as a guarantee that a code will never appear in the output--only
> that it will not appear as coded data.** See _Open questions_.

## Appendix

### Design rationale--how these decisions took shape

1. **The pass location was decided by a fact in the code, not a preference.** The
   initial instinct was "a pre-processing step inside section processing."
   Reading `refine_eicr` overturned it: `retain`, narrative-only, and system-skip
   sections never reach the matching engines. That single structural fact is the
   load-bearing reason for B1 over B3.

2. **"Search everywhere" split into two axes.** Once this was a whole-document
   pass, the temptation was a generic scanner. Separating _coverage_ from
   _pruning strategy_ let overrides reuse the surgical container logic the
   positive path already encodes.

3. **The ordering question got a better answer than the one first written.** The
   first draft justified the pre-pass with precedence and "clarity." Review
   pointed out that a post-pass tells the precedence story just as well. The real
   discriminator is narrative reconstruction--see _Ordering_ above.

4. **Reuse only what a second consumer proves.** Rather than abstract refinement
   into a kit of primitives up front, we extract only the piece both paths
   certainly need--the finder--and let _writing_ overrides reveal the shape of
   anything else. The enrichment seam is the payoff: we would not have discovered
   that enrichment was entangled in the finder until a second consumer needed a
   _non-mutating_ find.

5. **Provenance was shaped by _why_ the feature exists.** Because codes are
   overridden for their sensitivity, detailed provenance would re-leak what the
   removal was meant to hide. That constraint--not convenience--drove the
   content-free footnote line.

### Storage

Scope is the configuration. Mirror `custom_codes`, which is the closest existing
analogue (a jurisdiction's own per-configuration code list):

```sql
-- override_codes: codes that must NEVER appear in the output for a
-- configuration, regardless of section instructions.
CREATE TABLE override_codes (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    configuration_id UUID NOT NULL
        REFERENCES configurations(id) ON DELETE CASCADE,
    system_id UUID NOT NULL REFERENCES systems(id),
    code TEXT NOT NULL,
    display TEXT NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),

    UNIQUE (configuration_id, system_id, code)
);
```

Two notes carried from review:

- `ON DELETE CASCADE` is deliberate. Its absence on the exclusions table produced
  a `ForeignKeyViolation` whenever a configuration (or one of its conditions) was
  deleted after a code had been excluded.
- Unlike exclusions, overrides are **not** an FK into `codes`. A jurisdiction may
  need to override a local or proprietary code that TES never contributed, so the
  table carries `(system_id, code, display)` like `custom_codes` rather than
  referencing a curated row.

> [!NOTE]
> **Reseed persistence--decide before relying on any per-configuration table.**
> `seed_db.py` clears tables with `TRUNCATE ... RESTART IDENTITY CASCADE`
> (`refiner/scripts/seeding/seed_db.py:23-34`), and `configurations` is in that
> set. Postgres cascades a truncate to every table referencing a truncated
> one--so `custom_codes` does **not** survive a reseed today, despite being
> absent from the explicit list. `override_codes` inherits this. The real
> question is whether `seed_db.py` is ever run against a database holding live
> jurisdiction configs; if so, per-configuration user state is _already_ at risk
> today. **This is not caused by this ADR and should be tracked as its own
> issue.**

### Grouping in the payload

Open from review: how overridden codes are grouped for the UI. Because the scope
is configuration-wide, the deny-set has no condition axis to group by, so the
natural grouping is by code system--the same shape `CodeSystemSets` already uses.
If the UI needs categories (e.g. "behavioral health"), that is a labelling
concern on the DB row, not a change to the payload.

# app/services/terminology.py--carried on ProcessedConfiguration

class ProcessedConfiguration:

No `augmentation_timestamp` is needed: the pass does not mint its own footnote.
It reports masked sections back to `refine_eicr`, which stamps `content_masked`
onto the section's existing provenance record--and that footnote already carries
the run's timestamp.

### The pipeline seam

```python
# app/services/pipeline.py, inside refine_for_condition (~line 298)

eicr_plan = create_eicr_refinement_plan(...)

# NEW: overrides run FIRST, across all sections, ignoring section instructions.
# removing overridden codes before refinement means the refinement pass--which
# only RETAINS what is present--can never re-introduce them. precedence
# (override > include) falls out of ordering, and narrative reconstruction
# never sees the overridden data. reuse the spec the plan already loaded.
override_plan = create_override_plan(processed_configuration, eicr_plan.specification)
masked_section_codes = apply_overrides(eicr_root=eicr_root, plan=override_plan)

refine_eicr(
    eicr_root=eicr_root,
    plan=eicr_plan,
    masked_section_codes=masked_section_codes,
)
```

### The container-prune inversion (the one genuinely new bit of logic)

In positive refinement, `_prune_at_container_level`
(`refiner/app/services/ecr/section/entry_matching.py:466`) **keeps** matched
containers and removes the rest. Overrides want the opposite. Same rule metadata,
inverted keep/drop:

| Rule metadata               | Positive (refine)                  | Subtractive (override)                 |
| --------------------------- | ---------------------------------- | -------------------------------------- |
| `preserve_whole_entry=True` | matched entry kept intact          | matched entry **removed** intact       |
| `prune_container_xpath` set | keep matched containers, drop rest | **drop** matched containers, keep rest |
| default                     | keep matched entry, drop unmatched | **drop** matched entry                 |

> [!NOTE]
> **`prune_container_guard_xpath` is unnecessary in subtractive mode.** In
> positive refinement the guard protects shared, non-matching context (e.g. the
> Results Specimen Collection Procedure) from collateral pruning. Overrides only
> ever remove a container that _itself_ carries an overridden code, so shared
> context is safe by construction. If a jurisdiction genuinely overrides the code
> on a shared container, removing it is the requested behavior.

> [!CAUTION]
> **CDA cardinality.** The safe removal primitive is "remove the entry or
> container that the overridden code _defines_," never "delete the code element
> in place." An `observation` `SHALL` carry a `value`; deleting a leaf `<code>`
> and leaving its parent produces a schema-invalid entry. `preserve_whole_entry`
> and the container xpaths already point at removable structural units.

> [!CAUTION]
> **Emptied sections need `nullFlavor`.** Today `nullFlavor="NI"` is set on an
> emptied section _only inside the matching engines_. This pass runs over **all**
> sections, and `retain` / narrative-only / skip sections never reach those
> engines. So if it removes the last `<entry>` from a retained refinable section,
> nothing downstream sets `nullFlavor` and the document is schema-invalid. The
> pass must apply `nullFlavor="NI"` itself whenever it empties a section.

### Implementation sequencing (YAGNI-first)

What is shared vs. divergent between refine and override:

- **Shared, already code-set-agnostic--the _finder_.** `_find_matching_entries`
  (`entry_matching.py:256`) / `_try_match_entry` (`entry_matching.py:289`) already
  take `code_system_sets` as a parameter and do not care whether those codes are
  "wanted" or "denied." The one obviously-correct extraction.
- **Divergent--the _pruner_.** Positive keeps matched; overrides drop matched.
  `_prune_at_container_level` bakes the "keep matched" polarity in.
- **Positive-only**--enrichment, match comments, narrative reconstruction.

> [!IMPORTANT]
> Snapshots protect us from _regressing the positive path_; they cannot tell us
> an abstraction is the right shape for overrides. We only learn that by writing
> overrides. So do not abstract the pruner before the second consumer exists.

The extraction has one real seam beyond the mechanical move: **displayName
enrichment.** Today `_try_match_entry` calls `_enrich_display_name(el, coding)`
inline the moment it matches, mutating the element mid-find. A finder shared with
overrides must not mutate (we are about to _delete_ those elements), so
enrichment moves to the caller. The tempting shortcut--"delete the inline call,
let STEP 4's `enrich_surviving_entries` cover it"--is **not snapshot-safe**: STEP
4 resolves the display via each element's own `@codeSystem`, while the inline call
uses the _rule's_ `code_system_oid`, which is often `None` or a semantic OID that
disagrees. When they diverge, STEP 4 misses an element inline enrichment would
have labeled. The lossless fix: the finder returns matches carrying
`matched_coding`, and the positive caller enriches from that.

### Provenance

- **No per-entry comments.** A removed entry has no anchor, and an orphan
  "removed" comment next to a surviving entry's "matched" comment is
  contradictory at a glance.
- **One generic per-section footnote line.** When anything is removed from a
  section, its existing provenance footnote (rendered by
  `append_section_provenance_footnote`) gains a single line: _"Data in this
  section was masked."_ No code, no count, no domain.
- **Nothing in the trace, for now.** No consumer is asking for it. If an
  itemized, jurisdiction-facing audit is ever needed, the sidecar is the place
  (it does not ship inside the eICR).

Wiring: `SectionProvenanceRecord` gains `content_masked: bool = False`;
`apply_overrides` returns the set of masked section LOINC codes; `refine_eicr`
takes them as a defaulted parameter and folds the flag into the
`dataclasses.replace` where it already finalizes each record; the footnote writer
renders one italic sibling paragraph when the flag is set. Rendering it as a
sibling (not a new table column) keeps unmasked sections byte-identical, so
existing provenance snapshots do not churn.

> [!NOTE]
> The per-section line reveals _which_ section had content masked, but nothing
> about _what_. That is a deliberate tradeoff--the fact that a section was
> refined is already implied by the document being a refined eICR.

### Test scenarios (checklist)

The container inversion is the risky part. Fixtures build on the existing
`all_sections_covid_influenza` pair; each case is also a `content_masked`
assertion.

| #   | Scenario                                                                     | Expectation                                                                                                    |
| --- | ---------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| 1   | Override a code in a **Results** panel (container rule)                      | that sub-observation's container removed; siblings + guarded Specimen Collection Procedure survive; entry kept |
| 2   | Override a code in a **Medications** entry (`preserve_whole_entry`)          | whole entry removed; no partial excision                                                                       |
| 3   | Override the **only** matching code in a default-strategy section            | whole entry removed                                                                                            |
| 4   | Override a code in a **`retain`** section                                    | entry removed even though refinement never processes that section (coverage proof)                             |
| 4b  | Override a code appearing in a **narrative-only** section's `<text>`         | **nothing is removed**--pins the documented limitation so it is a known result, not a surprise                 |
| 4c  | Override a code in a `retain` section whose `<text>` names it                | entry removed, `<text>` **unchanged**--pins the coded-vs-narrative boundary                                    |
| 5   | Override a code that is **also in the want-set**                             | code absent from output; refinement did not re-introduce it (precedence)                                       |
| 6   | Override that removes the **last container**, emptying the entry             | entry removed too (not left hollow)                                                                            |
| 7   | Override that removes the **last entry** of a **retained refinable** section | section carries `nullFlavor="NI"`; document still schema-valid                                                 |
| 8   | Override a code on a **guarded shared-context** container (e.g. `17636008`)  | that container removed--the guard does not protect it in subtractive mode                                      |
| 9   | Override with an **empty deny-set**                                          | document byte-identical to the no-override run; `content_masked` false everywhere                              |
| 10  | Section with an overridden code **and** a wanted code in different entries   | only the overridden entry removed; the wanted entry survives to refinement                                     |
| 11  | Override a code in a section configured for **narrative reconstruction**     | reconstructed narrative never contains the overridden row (the ordering argument, asserted)                    |

The finder extraction's guardrail is the inverse: existing golden
`expected_eICR.xml` snapshots must be **unchanged** after it.

### Open questions

1. **Overlap with exclusion.** A code could in principle be both excluded
   (removed from want-set) and overridden (removed from output). These compose
   cleanly--exclusion stops retention, overrides remove anything present--but the
   UI should not offer both toggles on the same code in a way that reads as
   contradictory. Reviewed as "not something to worry about as part of this
   work."
2. **Category labelling.** Whether override rows carry a category (behavioral
   health, HIV status, …) for UI grouping, given provenance deliberately does not
   emit one.
3. **Narrative masking--the known gap, tracked separately.** Per the caution in
   _Decision Outcome_, overrides remove coded data only. The open decisions are
   (a) how the product describes the guarantee to jurisdictions in the meantime,
   and (b) what the follow-up actually does: resolve `<reference value="#id"/>`
   from an overridden entry to its narrative row and drop that row (bounded,
   works only where the sending EHR linked them properly), versus replacing the
   narrative wholesale where an override fires (safe, destroys a lot of wanted
   context), versus text-level matching (unbounded). Nothing here changes the
   design in this ADR; it builds on top of it.
4. **Jurisdiction-wide scope.** Deferred, with the reasoning in _Decision
   Outcome_. Worth revisiting once configuration-level overrides have real usage
   to learn from.
