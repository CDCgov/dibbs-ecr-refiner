# 16. naming conventions

Date: 2026-09-23

## Status

Proposed

## Context and Problem Statement

The same value carries a different name at almost every layer it passes through.
The clearest case is the human-readable label on a code:

| Layer           | Name                                                                               |
| --------------- | ---------------------------------------------------------------------------------- |
| TES ValueSet    | `concept[].display`, `expansion.contains[].display`                                |
| `tes/normalize` | `FhirCodeInfo.display`                                                             |
| `codes.csv.gz`  | `display`                                                                          |
| database        | `codes.display`, `custom_codes.display`, `events_custom_codes.name`                |
| db models       | `CodedConcept.display`, `DbCustomCodeUploadEvent.name`, `DbCodeResult.description` |
| refinement      | `Coding.display`, `matched_display`, `@displayName`                                |
| `active.json`   | `display`                                                                          |
| API             | `description`, `display`                                                           |
| client          | `code.description`                                                                 |

Four Python spellings (`display`, `display_name`, `description`, `name`) plus two
SQL aliases (`AS description` at
`refiner/app/db/configurations/codes/db.py:173,238`; `as code_name` at
`refiner/app/db/tes/db.py:233,249`) for one concept. The same pattern repeats for
a condition's name, a grouper's name and a code system's name--roughly ten names
each across four concepts. The full inventory is in the _Appendix_.

**The divergence is an accident of history.** Two migrations renamed the same
column concept in opposite directions three months apart:

- `migrations/20260615135704_rename_codes_columns.sql:6` -- `codes.name` -> `codes.display`
- `migrations/20260813142548_generalize_context_grouper_table.sql:3` -- `conditions_context_groupers.name` -> `display_name`

Nobody reconciled them. Five tables now say `display_name` and two say `display`,
with no semantic distinction. `display_name` is already the majority elsewhere
too: `refiner/app/services/ecr/` uses it 57 times against three reads of
`Coding.display`, and the collision is visible inside a single function--

```python
# refiner/app/services/ecr/section/utils.py:147,159-160
def _enrich_display_name(code_element: _Element, coding: "Coding") -> None:
    ...
    if coding.display:
        code_element.set("displayName", coding.display)
```

> three spellings of one concept in two lines, inside a function named for the third

**The same failure has reproduced elsewhere**, which is what makes this a
convention problem rather than a cleanup. Two more dead-even splits, each with a
rename performed mid-assignment:

| Concept                   | Spelling A                      | Spelling B                                | The seam                                                                     |
| ------------------------- | ------------------------------- | ----------------------------------------- | ---------------------------------------------------------------------------- |
| a configuration's version | `config_version` (24)           | `configuration_version` (24)              | `services/pipeline.py:302` -- `config_version=context.configuration_version` |
| a condition's URL         | `condition_url` (24, in `tes/`) | `condition_canonical_url` (24, in `app/`) | `tes/verify/database.py:233` -- `SELECT c.canonical_url AS condition_url`    |

### The boundaries the application actually has

Underneath the spelling problem is a structural one: **a model's name does not
say which boundary it crosses**, so nothing signals when a rename is local and
when it is a contract change.

The refiner's architecture is essentially "three runtimes, one core." Three
boundaries follow, and each has different rules about who may change a name:

| Boundary            | What crosses                        | Naming family today    |
| ------------------- | ----------------------------------- | ---------------------- |
| server <-> database | psycopg rows                        | `Db*`                  |
| server <-> browser  | OpenAPI, generated by orval into TS | `*Response` / `*Input` |
| server <-> Lambda   | `active.json` in S3                 | **unnamed**            |

The third boundary is real, versioned and cross-deploy. `active.json` is written
by the web app and read by a separately built Lambda image behind an
exact-equality `schema_version` gate (`app/lambda/lambda_function.py:730`), with
a formal JSON Schema (`tests/fixtures/activations/active_config_payload_schema_v1.json`,
`additionalProperties: false`) and an ops job for migrating it
(`ops/reactivations/regenerate_active_configs.py`). Nothing in the name
`CodeSystemSets.to_dict()` says any of that.

The cost of that silence is already on disk. `to_dict` writes
`{"code", "display", "system"}` (`app/services/terminology.py:152-162`) while
`from_dict` reads `item.get("system_oid", "")` (`:200`), so **every `Coding` the
Lambda reconstructs from S3 has `system_oid=""`**. It is harmless today only
because `Coding.system_oid` is read in exactly one place in the codebase--the
`to_dict` that writes it. The round trip is not identity, the two runtimes hold
different values for the same object, and no test asserts otherwise.

The first boundary is equally load-bearing and equally unmarked.
`Dockerfile.lambda:22-24` ships `app/core`, `app/services` and `app/db` and
**not `app/api`**--deliberately, because the Lambda reads `active.json` from S3
and processes eICR/RR pairs off SQS and has no use for the web interface. The
API layer exists to author configurations and to test individual eICR/RR pairs;
that separation is why `app/services/ecr` is large and deliberately free of
database calls. Yet `app/db` imports HTTP request models from `app/api` in four
places, and `app/services/conditions/refinement.py:3` does too. None is reachable
from the handler today; any that becomes reachable is a cold-start
`ModuleNotFoundError` in production, not a style complaint.

A reader who encounters `display`, `display_name`, `description` and `name` in
one request path cannot tell which differences are meaningful. A reader who
encounters `CodeSystemSets.to_dict()` cannot tell they are editing a deployment
contract. Both are the same defect: **names that do not carry the information a
reader needs in order to act safely.**

> [!NOTE]
> **`display_name` already has prior art in this directory.** ADRs
> [0005](0005_2026-02-18_display-name-enrichment.md),
> [0007](0007_2026-03-07_display-name-enrichment-and-better-search.md) and
> [0008](0008_2026-03-25_s3-adjustments-for-display-name.md) all use "display
> name" as the term of art. The decision record settled the vocabulary; the
> columns drifted from it afterwards.

## Decision Drivers

- **Applicable without domain knowledge.** A rule requiring an engineer to know
  which types mirror FHIR is a rule they will apply inconsistently. It has to be
  mechanical.
- **A name should say which boundary it crosses.** Renaming a field inside the
  server is free; renaming one in `active.json` is a data migration. The name is
  the only place that distinction can live where every call site sees it.
- **Do not churn what we do not own.** Keys in someone else's format, strings
  design chose, and file headers users author are out of scope by definition.
- **Grep-verifiable.** Each rule should be checkable in one command, so it can be
  enforced in review rather than remembered.
- **Simple over complete.** Fewer families, fewer exceptions. A convention with
  four carve-outs is not a convention.
- **One effort, one record.** These renames only make sense as a set; landing
  them piecemeal leaves the codebase looking more arbitrary, not less.

## Considered Options

### Naming the human-readable label

#### A. `display_name` for every identifier we control (RECOMMENDED)

One spelling in the database, the db models, the services layer, the API and
`active.json`. String keys addressing a foreign format keep that format's
spelling.

**Pros**: already the majority (five tables, 57 uses in `services/ecr/`, three
ADR titles); reads unambiguously where a bare `display` reads as a verb; matches
the export headers and the custom-code upload header, so the user-facing boundary
needs no translation.

**Cons**: more characters at every call site; renaming `CodeRow.display`
regenerates the committed `.csv.gz` files; and renaming it in `active.json` is a
schema version bump with a reactivation run behind it (see _Sequencing_).

#### B. `display` everywhere

**Pros**: shortest; matches the FHIR source key exactly.

**Cons**: loses against the existing majority, so it is the larger diff. Collides
with the verb sense throughout the refinement code, where "display" is something
the app _does_ to a document. Forces renaming `conditions.display_name`,
`valuesets.display_name` and `systems.display_name`, the columns most referenced
across the query layer.

#### C. Layer-scoped conventions, documented

Keep `display` in the database and `display_name` above it.

**Pros**: no migration; the boundary is explicit.

**Cons**: institutionalizes a translation rather than removing it, and every new
field must decide which side it is on. It does not generalize--the
`config_version` and `condition_url` splits do not fall on layer boundaries, so a
layer-scoped rule cannot fix them. Rejected as a rule that needs exceptions on
the day it is written.

### Marking which boundary a model crosses

The `Db` prefix was introduced to signal "this came from the database--you are
working with a lower-level model." That intent is right and worth keeping. The
problem is that it is the _only_ boundary marked, it is applied to three
different kinds of thing, and eight `Db*` types are generated into the client
(`client/src/api/schemas/db*.ts`). It has also stopped being load-bearing:
`DbTesConfigsToUpdateResponse` carries both the prefix and the `Response` suffix.

`DbCode` shows the drift. It is not a row:

```
codes table:  id, display, code, system_id, created_at, updated_at
DbCode:           display, code, system_id, system_name
```

`system_name` is a join onto `systems.display_name`; `id` and the timestamps are
dropped. `DbCode` has always been a response shape wearing a db-facing name, as
have `DbTotalConditionCodeCount` (an aggregate with no table), `DbCodeResult` (a
paginated projection) and `DbConfigurationSectionProcessing`.

#### D1. One family per boundary (RECOMMENDED)

Three boundaries, three families, and every model belongs to exactly one:

- **`Db*`** -- a row or projection the server reads from Postgres. Never
  generated to the client, never referenced from `app/api`.
- **`*Response` / `*Input`** -- crosses to the browser. Generated by orval;
  renaming a field here is a client change.
- **`*Payload` / `*Metadata`** -- crosses to the Lambda via S3. Versioned;
  renaming a field here is a data migration. `ConfigurationStoragePayload` and
  `ConfigurationStorageMetadata` already fit; the `active.json` code and section
  shapes need to join them rather than remaining anonymous dicts produced by
  `to_dict`.

Anything belonging to no boundary--persisted enums like `DbNarrativeAction`,
`DbSectionAction`, `DbSectionType`, `DbConfigurationStatus`--is domain
vocabulary, not a model. It loses the prefix and is shipped to the client freely;
the client already branches on `DbSectionAction.refine`
(`client/src/pages/Configurations/CustomizeSections/Sections/index.tsx:399`).
`app/db/configurations/labels.py` is the existing precedent, written deliberately
so orval can ship it.

**Pros**: adds no layer and no models. The response models already exist for
every true row model (`DbCustomCode` -> `CustomCodeResponse`, `DbConfiguration`
-> `GetConfigurationResponse`, `DbCondition` -> `GetConditionResponse`), so this
is a rename. It makes the `active.json` boundary visible for the first time,
which is the boundary that has already drifted. And it gives the rule a test an
engineer can apply alone: _if you cannot name the boundary, the model is in the
wrong place._

**Cons**: the three families need judgement at the margin, which is what this
document is for.

#### D2. Drop the `Db` prefix entirely

**Pros**: no judgement needed.

**Cons**: discards a signal the team adopted on purpose, and leaves all three
boundaries unmarked instead of one. The prefix is not the problem; its
application to non-rows is.

#### D3. A DTO triad per entity

The textbook split (FastAPI's `UserIn`/`UserOut`/`UserInDB`, DRF's Model +
Serializer).

**Pros**: complete decoupling by construction.

**Cons**: `app/db` and `app/api` already hold roughly 192 model classes to serve
46 routes; a triad per entity grows that number rather than reducing it, and most
additions would be identity mappings. It fixes the symptom--types crossing
layers--by adding types, without addressing the direction that let them cross.
That is E1's job, below.

### The junction table name

`conditions_codes_temp` is the permanent membership junction, referenced 43 times
across `app/`, `ops/` and `tes/`. The `_temp` suffix is a leftover; a dead
`conditions_codes` table also remains, which nothing queries (the docstring at
`refiner/app/db/conditions/db.py:277` still claims to, but the query below it
reads `conditions_codes_temp`).

| Option                           | For                                                                     | Against                                                                                                                 |
| -------------------------------- | ----------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| `conditions_codes`               | shortest; reuses the freed name                                         | needs the dead table dropped first, muddying migration history; reads as a two-way join when the grain is three columns |
| **`conditions_codes_valuesets`** | names every entity in the grain, which is the thing that gets forgotten | long                                                                                                                    |
| `memberships`                    | matches `memberships.csv.gz`, aligning database with processed data     | a bare noun that does not say membership _of what_                                                                      |

### Whether `app/db` should be a real data layer

`app/db` is 5,581 lines across 25 files (89 async functions, ~100 model classes);
`app/api` is 6,328 across 31 (46 routes, ~92 model classes); `app/services` is
13,617 across 53. At that size the dependency direction between them should be a
property of the code, not a habit. It currently is not:

**1. `app/db` imports HTTP request models from `app/api`.** Four sites:
`configurations/db.py:8` (`AddSectionInput`, `DeleteSectionInput`),
`configurations/codes/db.py:8` (`FilterInput`),
`configurations/custom_codes/db.py:5` (`AddCustomCodeInput`),
`simulator/model.py:3`. The data layer's signatures are shaped by request bodies,
and `app/api` is not shipped in the Lambda image.

**2. `app/db` returns an API response model.** `get_configuration_versions_db`
(`app/db/configurations/db.py:935,962`) declares
`-> list[GetConfigurationResponseVersion]`.

**3. `app/db` performs orchestration.** `app/db/configurations/db.py:17` imports
`insert_event_db`, so configuration mutations write audit events inline--a
business rule inside data access, and part of why that module is 1,068 lines.

**4. `app/db` contains a cycle it already pays to work around.**
`app/db/tes/db.py:824` and `:864` both carry the comment
`# Local import to avoid circular dependency: tes.db -> configurations.db -> conditions.db -> tes.db`,
with a third deferred import at `:893`. The loop is real and lives entirely
inside `app/db`; it is invisible to a module graph only because someone already
paid for it with function-local imports.

A fifth, smaller: there is no single row-to-model convention. `class_row` appears
51 times and `dict_row` 47, so half the queries produce typed rows and half
produce dicts that are hand-mapped afterwards.

> [!NOTE]
> **This is why the layering question belongs beside the naming question.**
> Defect 1 means renaming an API request model edits files in `app/db`. The
> layering defect makes the rename harder, and the rename is what surfaced the
> layering defect.

#### E1. Enforce the dependency direction (RECOMMENDED, deferred)

A total order: `core < db < services < api`. `app/db` imports nothing from
`app/services` or `app/api`; `app/services` imports nothing from `app/api`. db
functions take primitives or db-owned parameter objects instead of request
models; `GetConfigurationResponseVersion` moves to `app/api`; event writes and
default-section construction move up into `app/services`; shared utilities
`app/db` legitimately needs move to `app/core`.

**Pros**: removes defects 1-3, adds no layer and no models, and makes the
boundary the Lambda image already enforces at deploy time enforceable at author
time. An import-graph test asserts it and keeps it asserted.

**Cons**: touches the two largest db modules (`configurations/db.py` 1,068 lines,
`tes/db.py` 931), and moving event writes changes transaction boundaries on an
audit trail. Real work, not mechanical. Defect 4 needs a separate acyclicity
check--a direction rule between layers cannot express a loop within one.

#### E2. E1, plus repository objects

**Cons**: the repo prefers functions over classes, and the per-domain `db.py`
modules already provide the grouping a repository class would. The measured pain
is direction, not grouping. Revisit only if E1 lands and grouping still hurts.

## Decision Outcome

Option **A** for the label, **D1** for the boundaries,
**`conditions_codes_valuesets`** for the junction, and **E1** as the layering
direction.

A, D1 and the junction rename are this effort. **E1 is a direction, not a commit
in this PR**--it touches the two largest db modules and is not mechanical. Rules
1-8 stand on their own and do not depend on E1 landing.

### The rules

**1. One name per concept.**

| Concept                   | Name                     | Retires                                             |
| ------------------------- | ------------------------ | --------------------------------------------------- |
| a human-readable label    | `display_name`           | `display`, `description`, `name`, `code_name`       |
| a versioned identity URL  | `<entity>_canonical_url` | `condition_url`, `cond_url`                         |
| a configuration's version | `configuration_version`  | `config_version`                                    |
| a count of codes          | `code_count`             | `total_codes`, `total_code_count`, `code_set_count` |

**2. Every identifier we control that names a human-readable label is
`display_name`. String keys addressing a foreign format keep that format's
spelling.** `concept.get("display")` reads a key in a document TES publishes;
`element.set("displayName", ...)` writes an attribute in the HL7 CDA schema.
Neither is a name we chose, and neither is an identifier. Everything else is
ours--including `active.json`, which we write and read on both sides.

**3. A model's name says which boundary it crosses.** `Db*` for a row or
projection out of Postgres, never generated to the client and never referenced
from `app/api`. `*Response` / `*Input` for the browser. `*Payload` / `*Metadata`
for `active.json`. A model that crosses no boundary is domain vocabulary and
carries no prefix. If you cannot name the boundary, the model is in the wrong
place.

**4. Request and response suffixes.** `*Input` for request bodies (16 of 19
today; `ApplyTesUpdatesToDraftsRequest`, `CreateDraftsFromActiveConfigsRequest`
and `UpdateUserNotificationsRequest` are renamed). `*Response` for anything a
route returns. `*Result` is reserved for internal pipeline outputs
(`RefinementResult`, `SectionRunResult`, `AugmentedResult`), which is why
`DbCodeResult` is renamed out of it.

**5. A table whose grain is a composite membership names each entity in the
grain.** `conditions_codes_valuesets` has a three-column key, so a code belonging
to eight sibling groupers is eight rows and every aggregate over it must
deduplicate. The name is what makes that legible at the call site. This is not a
general rule for every table with two foreign keys--it is a rule for tables whose
grain is routinely misread, and this is the one we have.

**6. Database access functions end in `_db`.** 78 of 89 already do. Private
helpers within a db module (`_clone_code_exclusions`, `_raise_if_*`) are exempt;
public ones are not (`is_event_valid`,
`get_custom_code_upload_events_by_event_id`, `get_configurations_set_to_tes_version`).

**7. Identifier spelling and user-visible strings are separate decisions.**
Identifiers standardize; display strings are whatever design specified. "Code
set" is the worked example: the UI says _code set_, so the string stays exactly
as designed, while the identifier spelling settles on `code_set` / `CodeSet`
(today it is also `codeset`, `Codeset` and `codeSet`).

**8. Model kind follows trust, not layer.** Dataclasses by default, including for
rows out of the database--`class_row(SomeDataclass)` gives psycopg a real
constructor, attribute access and mypy coverage, and the codebase has already
voted (`app/db` holds 48 dataclasses against 2 `TypedDict`). Pydantic only where
data arrives from a source that must be verified before the app acts on it. TES
content already clears that bar upstream, validated by `fhir.resources` during
normalize. **`active.json` read-back does not**: it is written by a different,
possibly older deploy and gated on an exact-equality `schema_version`. Reads of
it are strict--`item["k"]`, not `item.get("k", "")`--so a contract mismatch fails
loudly at cold start instead of silently emptying a clinical field.

### What deliberately does not change

> [!IMPORTANT]
> These are out of scope by rule, not by oversight. A naming PR that touches them
> is a product change.

- **Keys in formats we consume or emit.** `concept[].display` and
  `expansion.contains[].display` from TES; `@displayName`, `@codeSystem` and
  every other CDA attribute.
- **User-visible strings.** Column headers in the CSV exports ("Code System",
  "Code", "Status", "Display Name", "Source(s)") and every label in the SPA.
  Governed by design and UX.
- **The custom-code upload CSV contract.** Header `code,code_system,display_name`
  (`app/api/v1/configurations/custom_codes/custom_codes.py:231,334`) and the
  values in its `code_system` column. Users author these files. The header
  already agrees with Rule 1.
- **The two `CODE_SYSTEMS` tables.** `tes/normalize/model.py` decides which
  published codes survive; `ops/seeding/systems.py` defines what the application
  can store. Both docstrings explain the split and `tes/verify/database.py`
  asserts they cannot drift.

`active.json` is **not** on this list. It is a contract we own on both sides, it
falls under Rule 2, and it has a migration mechanism built for exactly this.

### Sequencing

One pull request, ordered commits, one concept per commit so each is
grep-verifiable in review.

1. Rename the four leaking `Db*` types and move the persisted enums to a domain
   module (Rule 3). **First**: once `DbCode` is no longer the client's type, the
   column renames are server-internal.
2. `display_name` unification in the database, db models, SQL aliases and API
   fields.
3. `active.json`: `display` -> `display_name`, `schema_version` -> 2, strict
   reads per Rule 8, and the `*Payload` family applied to the code and section
   shapes. Exercise `ops/reactivations/regenerate_active_configs.py` end to end
   with DevOps before merge--this is the first real test of that mechanism, and
   the one commit that can degrade refined output if it is wrong.
4. `CodeRow.display` -> `display_name` and the regenerated `.csv.gz`, in a commit
   of its own.
5. Table, model and constraint renames; drop the dead `conditions_codes`.
6. The small ones: the duplicated `_get_code_set_status`, `CodeSystemsReponse`,
   the `_db` suffix misses, `Config` -> `Configuration`.

> way--`ops/seeding/load_processed_data.py:125` issues

> around the bulk load inside the fail-fast `ops prepare-db` chain. Renaming the
> table without them leaves a 27th stale-constraint case; renaming them without
> updating that tuple breaks seeding.

### Open questions

1. **Does the client's code label field become `display_name` on the wire?**
   Rule 1 says yes. Client and server ship as one image (`Dockerfile.app:18,64`)
   with no third-party consumers, so no deprecation window is needed and
   `tsc --noEmit` finds every type-level break. Non-type-level uses--CSV export
   headers, `Object.keys`, sort keys, `any`-typed fixtures--still need eyes.
2. **Whether `condition_url` in `tes/` converges on `condition_canonical_url`.**
   The split is currently layer-clean and the processed CSV headers are part of
   the data contract. Converging is more consistent; leaving it means documenting
   the seam at `tes/verify/database.py:233`.
3. **Whether the completeness derivation collapses to one implementation.**
   Rule 1 names the concept but does not decide whether `valuesets.completeness`
   keeps storing a derived string while `conditions.coverage_level` stores the
   raw one. A data-model question, likely its own ADR.
4. **What enforces Rule 3 and E1 six months from now.** An import-graph test is
   the obvious mechanism and needs no new dependencies. Lint configuration is
   being reworked separately and should not be entangled with this.
